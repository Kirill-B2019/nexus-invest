# Техническое задание: раздел «Уведомления» в закрытой части (ЛК)

## 1. Назначение

Реализовать в личном кабинете (ЛК) раздел **системных и ручных уведомлений** с отображением в верхнем меню (колокольчик), отдельной страницей списка и админ-интерфейсом создания уведомлений для роли с правом.

---

## 2. Требования к данным

### 2.1 Хранение

- Использовать стандартный механизм Laravel Notifications и таблицу `notifications` (миграция `php artisan notifications:table` при необходимости).
- Каждое уведомление привязано к пользователю (получателю).
- Дополнительные поля хранить в JSON `data` уведомления.

### 2.2 Поля в `data` (расширяемая структура)

- **type** — тип: `system` | `manual`.
- **title** — заголовок (строка).
- **body** — текст уведомления (строка).
- **link** — необязательная ссылка при клике (строка, URL или путь).
- **importance** — важность: `low` | `normal` | `high` | `urgent` (по умолчанию `normal`).
- **expires_at** — необязательная дата/время окончания действия (ISO 8601 или `null`). После этой даты уведомление не показывать в активных списках (или показывать только в разделе «Истёкшие»).
- **created_by** — для ручных: ID пользователя-отправителя (при наличии).

### 2.3 Срок (expires_at)

- Если `expires_at` задано и меньше текущего времени — уведомление не выводить в колокольчике и в списке «Активные» (или скрывать по умолчанию).
- Опционально: фильтр/вкладка «Истёкшие» на странице уведомлений.

### 2.4 Важность (importance)

- Использовать для сортировки (сначала более важные) и отображения (иконка/цвет/бейдж в списке и в колокольчике).
- Значение по умолчанию при создании — `normal`.

---

## 3. Роли и права

- **Просмотр своих уведомлений** — у всех пользователей с доступом в ЛК (middleware: `auth`, `verified`, `lk.access`).
- **Создание и рассылка уведомлений** — по разрешению, например `manage-notifications`:
  - создать разрешение и при необходимости роль (например, «Администратор уведомлений»);
  - выдать разрешение нужным ролям;
  - маршруты админ-раздела защищать middleware `permission:manage-notifications`.

---

## 4. Функционал для пользователя ЛК

### 4.1 Колокольчик в topbar

- Заменить заглушку в `resources/views/layouts/app/topbar.blade.php`: подгружать реальные данные (последние N непрочитанных, счётчик непрочитанных).
- Учитывать `expires_at`: не показывать истёкшие.
- Сортировка: по важности, затем по дате.
- В выпадающем списке: заголовок, дата, индикатор важности; по клику — переход по `link` (если есть) и пометка прочитанным.
- Счётчик — число непрочитанных (не истёкших). Убрать захардкоженное значение «3».
- Ссылка «Все уведомления» внизу дропдауна → страница списка уведомлений.

### 4.2 Страница «Уведомления» (`/lk/notifications`)

- Список уведомлений текущего пользователя с пагинацией.
- Учитывать `expires_at`: по умолчанию показывать только активные (не истёкшие).
- Фильтры: все / только непрочитанные; опционально — «Истёкшие».
- Сортировка: важность, затем дата.
- Действия: отметить прочитанным, «Отметить все прочитанными».
- В каждой строке: тип (системное/ручное), важность, заголовок, краткий текст, дата, ссылка (если есть).

---

## 5. Функционал для создателя уведомлений (роль с правом)

### 5.1 Раздел администрирования

- Раздел в ЛК, например `/lk/admin/notifications`, доступный по разрешению `manage-notifications`.
- Список отправленных уведомлений (опционально): кто создал, дата, аудитория, заголовок — для истории и аудита.

### 5.2 Форма создания уведомления

- Поля:
  - заголовок (обязательно);
  - текст (обязательно);
  - ссылка (необязательно);
  - **важность** — выпадающий список: Низкая / Обычная / Высокая / Срочная (значения `low`, `normal`, `high`, `urgent`), по умолчанию «Обычная»;
  - **срок действия** — необязательное поле даты/времени (до которого уведомление активно); подпись вроде «Не заполнять — без срока»;
  - аудитория: «Всем пользователям ЛК», «По роли» (выбор роли), при необходимости «Конкретный пользователь».
- Валидация: заголовок и текст обязательны; при указании срока — `expires_at` в будущем.
- При сохранении создавать записи в таблице `notifications` для каждого получателя с заполненным `data` (включая `importance`, `expires_at`, `type: manual`, `created_by`).

---

## 6. Системные уведомления

- Реализовать возможность генерировать уведомления из кода (события: публикация новости, смена роли, дедлайны и т.п.).
- Использовать канал `database` и классы Laravel Notification; в `data` передавать `type: system`, при необходимости подтип события, `importance` и `expires_at`.
- Документировать в коде или в правилах проекта, какие события создают уведомления и какие у них важность и срок.

---

## 7. Технические требования

- Модель User: trait `Notifiable`, использование канала `database`.
- Маршруты: под существующими middleware ЛК (`auth`, `verified`, `lk.access`); админ-раздел — дополнительно `permission:manage-notifications`.
- Стили и вёрстка: в духе текущего ЛК (существующие layout, topbar, таблицы, формы); при необходимости доработать мобильную версию списка и колокольчика.
- Сообщения пользователю: по правилам проекта (например, SweetAlert2 в публичной части; в ЛК — по текущей практике).
- Язык интерфейса и комментариев: русский.

---

## 8. Документация и правила проекта

- **Добавить в правила проекта (например, в `.cursor/rules/` или в описание структуры) отдельный пункт о разделе «Уведомления»**, чтобы в дальнейшем агенты и разработчики могли:
  - находить код и конфигурацию, связанные с уведомлениями;
  - понимать, где настраивать типы, важность, срок и аудиторию;
  - безопасно дорабатывать раздел (новые типы системных уведомлений, новые уровни важности, изменения в колокольчике или на странице списка).
- В этом пункте указать:
  - назначение раздела (системные и ручные уведомления с сроком и важностью);
  - ключевые файлы/маршруты (контроллеры, представления, маршруты, миграции);
  - структуру `data` уведомлений и перечень полей (в т.ч. `importance`, `expires_at`);
  - разрешение `manage-notifications` и его использование;
  - где добавлять новые системные уведомления (примеры классов/событий).
- Цель: зафиксировать раздел в правилах для последующей настройки и изменений без потери контекста.

## 9. Порядок реализации (рекомендуемый)

1. Миграция таблицы `notifications` (если ещё нет), сидер разрешения и при необходимости роли.
2. Модель User: `Notifiable`, канал `database`.
3. Контроллер(ы) и маршруты для ЛК: список для колокольчика, список страницы, отметка прочитанным.
4. Обновление topbar: загрузка данных, счётчик, вывод списка с учётом срока и важности.
5. Страница «Уведомления»: список, фильтры, пагинация, отметка прочитанным.
6. Админ-контроллер и форма создания: поля важность и срок, аудитория, сохранение в `notifications`.
7. Пример одного системного уведомления (например, при публикации новости).
8. **Добавление в правила проекта пункта о разделе «Уведомления»** (см. п. 8).

---

## 10. Критерии приёмки

- В колокольчике отображаются только актуальные (не истёкшие) уведомления с корректным счётчиком.
- На странице «Уведомления» работают фильтры и сортировка по важности и дате; учитывается срок действия.
- Пользователь с правом `manage-notifications` может создавать уведомления с указанием важности, срока и аудитории; они доходят до выбранных пользователей.
- Системное уведомление (хотя бы одно) создаётся из кода и отображается в ЛК.
- В правилах проекта добавлен и сохранён пункт о разделе уведомлений для дальнейшей настройки и изменений.
